## Critical Voice UX Requirement — ChatGPT Advanced Voice Style

Replace the push-to-talk-first design with a real-time, full-duplex conversational voice interface similar to ChatGPT Voice.

### Required behavior
- Start a voice session with one button.
- Once the session starts, continuously listen for the user's speech without requiring a button press for every message.
- Automatically detect when the user has finished speaking using voice activity detection (VAD) and endpoint detection.
- Generate a response and speak it aloud automatically.
- Allow the user to interrupt the assistant naturally at any time. When the user starts speaking during playback, stop or cancel the current response immediately and prioritize the user's new speech.
- Maintain conversational context across turns.
- Handle natural pauses, short follow-ups, corrections, and people changing their minds mid-sentence.
- Avoid responding to the assistant's own voice as if it were the user. Use echo cancellation where available, plus appropriate microphone and playback handling.
- Show live states such as Listening, Processing, Speaking, and Reconnecting.
- Provide a visible microphone mute button and an obvious End Voice Session button.
- Support text input during a voice session.
- Do not require the user to press Enter, click Send, or press a microphone button for each turn.
- Do not repeatedly restart the conversation or play audio twice.
- Recover gracefully from microphone permission errors, device disconnections, model failures, and network interruptions.

### Architecture
Implement an event-driven voice session manager with explicit states and cancellation support. Separate audio capture, VAD, speech recognition, response generation, TTS playback, and interruption handling.

Prefer a streaming speech-to-speech API if a suitable provider is configured. Otherwise, implement a low-latency streaming pipeline:

Microphone → VAD → speech recognition → conversational model → streaming TTS → speakers.

Use WebRTC or compatible audio APIs when appropriate. For local operation, evaluate compatible VAD, local speech recognition, Ollama, and local TTS options. Keep providers replaceable.

Prevent microphone feedback and audio self-triggering. Use barge-in detection, playback cancellation, and turn IDs to discard stale responses after an interruption.

### UX goal
The interaction should feel like a natural ongoing conversation with ChatGPT Voice, not a walkie-talkie, dictation app, or ordinary chatbot with a microphone button.

Push-to-talk may exist as an optional fallback, but it must not be the default interaction.

Implement this in the actual project, test the full conversation loop and interruptions, and document any limitations. Do not simulate real-time conversation with prerecorded audio or fake listening indicators.

# 15. Multi-Agent Orchestration and Subagent Harness

Upgrade JARVIS to support a real multi-agent architecture with one central orchestrator and multiple specialized subagents.

## A. Main Orchestrator

The main JARVIS agent is the user's primary interface. It must:
- Understand the user's request and desired outcome.
- Decide whether the task can be completed directly or requires delegation.
- Break complex tasks into smaller, independent subtasks.
- Select appropriate subagents based on their capabilities.
- Dispatch independent subtasks concurrently when beneficial.
- Track task status, dependencies, progress, and deadlines.
- Collect and validate subagent results.
- Resolve conflicting results and request additional investigation when needed.
- Produce one coherent response to the user through voice or text.
- Cancel delegated work when the user cancels the parent task.

The orchestrator must remain responsible for the overall task and final response. Subagents should not independently send competing spoken responses to the user.

## B. Specialized Subagents

Create configurable agents with separate instructions, tool permissions, and optional model settings.

Initial agent roles:

1. **Research Agent**
   - Searches the web and investigates topics.
   - Extracts evidence and preserves source URLs.
   - Compares claims across sources.
   - Returns concise findings with citations and uncertainty notes.

2. **Study Agent**
   - Explains concepts, solves appropriate exercises, generates revision materials, and searches approved study documents.
   - Uses RAG to ground answers in uploaded textbooks and notes.
   - Adapts explanations to the user's requested difficulty.

3. **Coding Agent**
   - Inspects approved project workspaces.
   - Investigates bugs, proposes code changes, writes tests, and analyzes errors.
   - Runs only authorized commands.
   - Reports changed files and test results.

4. **Browser Agent**
   - Uses the Playwright browser harness.
   - Navigates pages, gathers information, interacts with forms, and returns structured results.
   - Requires approval for consequential actions.

5. **Memory and Knowledge Agent**
   - Searches approved memories, notes, and indexed documents.

   - Suggests useful memory updates but does not silently store everything.

6. **Planning Agent**
   - Breaks large goals into manageable tasks.
   - Identifies dependencies, milestones, and blockers.
   - Tracks progress and proposes next steps.

7. **Verification Agent**
   - Independently checks important factual claims, citations, calculations, code changes, and task completion.

Allow custom agents to be added through configuration rather than requiring code changes.

## C. Task Delegation and Parallel Execution

Implement a real task manager and delegation protocol.

Each delegated task must include:
- Unique task ID and parent task ID.
- Clear objective and acceptance criteria.
- Relevant context and input references.
- Allowed tools and permissions.
- Expected output format.
- Status, timestamps, and cancellation state.
- Results, errors, and evidence references.

Support the following task states:

`queued → running → waiting → completed / failed / cancelled`

The orchestrator should:
- Execute independent tasks concurrently.
- Respect dependencies between tasks.
- Limit concurrent agents and model requests.
- Apply per-task timeouts and retry limits.
- Support cancellation propagation.
- Avoid duplicate execution of the same task.
- Recover gracefully from subagent failures.
- Return partial results when a noncritical subagent fails.

Do not launch every agent for every request. Use the smallest team that can complete the task reliably.

Example: For an AI model research request, the Research Agent gathers current sources, the Coding or Technical Agent evaluates compatibility with the target hardware, and the Verification Agent checks the conclusions. The orchestrator combines their findings into one response.

- Allow shared references to documents, source URLs, code diffs, and intermediate results.

- Separate temporary task state from long-term user memory.
- Prevent one agent from silently changing another agent's instructions or permissions.
- Treat retrieved content, webpages, documents, and agent-generated messages as untrusted data.

Subagents must not inherit unrestricted filesystem, browser, shell, network, or memory access from the orchestrator.

All subagents must use the same central infrastructure:
- Tool registry and permission manager.
- MCP integrations.
- Browser automation.
- Agent Skills registry.
- RAG and document retrieval.
- Research and citation services.
- SSE event bus.
- Logging and cancellation system.

Agents may have different tool allowlists, but they must not bypass the central permission manager.

Skills can guide an agent's procedure, while tools perform the actual actions. Assign relevant skills to agents on demand rather than loading every skill into every agent.

## H. Live Agent Activity in the Center Notch

Display meaningful real-time activity through the existing SSE event system.

Examples:
- `agent.delegated`
- `agent.started`
- `agent.progress`
- `agent.waiting`
- `agent.completed`
- `agent.failed`
- `agent.cancelled`
- `orchestrator.synthesizing`
- `task.completed`

The expanded notch should show:
- The overall task.
- Which agents are active.
- Short status descriptions.
- Completed and pending subtasks.
- Tool execution activity.
- Errors requiring attention.

Provide a detailed task panel in the main application for inspecting agent outputs, evidence, and execution history.

Never display fabricated progress. Events must represent real task state.

## I. Security and Reliability

- Enforce a global concurrency limit and bounded delegation depth.
- Prevent recursive agent spawning without authorization.
- Require approval for consequential external actions.
- Keep secrets out of inter-agent messages and logs.
- Validate all tool arguments and structured results.
- Record which agent initiated each tool call.
- Cancel descendants when their parent task is cancelled.
- Use the verification agent selectively for high-impact or evidence-sensitive tasks.
- Do not let agents approve their own restricted actions.

## J. Implementation Order

1. Build the task manager and structured delegation interface.
2. Implement one orchestrator and two real subagents.
3. Add concurrent execution, dependencies, and cancellation.
4. Integrate tool permissions and shared RAG references.
5. Add research, study, coding, browser, planning, and verification roles.
6. Connect agent events to SSE and the central notch.
7. Add model routing, resource limits, logs, and automated tests.

Initially implement the Research Agent and Verification Agent as a proof of the delegation architecture. Confirm that they execute separate tasks, return real results, and are combined by the orchestrator before adding the remaining agents.

Do not implement fake agents that merely return hardcoded responses. Use actual model calls or explicitly defined deterministic tools, and test delegation, concurrency, failure recovery, and cancellation.
